# War Games — 2026-07-27, Anchorage k3s, Harness KubernetesDirect

Ten consecutive executions of the single E2E pipeline (provision →
route-contract → CLI quality gate) plus the earlier failure-variant pipelines,
run against a live cluster with deliberate sabotage between runs. Every
scenario behaved as designed; the analysis below scores the experience a
PayPal engineer would have at each failure.

## Ease-of-use analysis for PayPal engineers

**What's genuinely easy now**
- **Day one is one pipeline run.** From nothing — not even a workspace — to a
  green contract gate in under 4 minutes, with no manual Postman setup at all.
  The provision stage creates or adopts everything and feeds IDs downstream.
- **Recovery is always "rerun".** After an outage, a bad credential, or a
  failed run, there is nothing to clean up; idempotent adoption guarantees
  reruns converge. This is the property that makes the pipeline safe to wire
  into CI triggers.
- **Failures are cheap and early.** Every sabotage was caught at the earliest
  possible step, and every downstream step was skipped — no partial writes, no
  half-configured Postman state to untangle.
- **Two views of every result.** Harness gets JUnit; the same runs appear in
  the Postman workspace run history — engineers can debug in whichever tool
  they already live in.

**Where an engineer would stumble (ranked, with fixes)**
1. **Raw exit codes on infrastructure failures.** The outage drill surfaced
   "exit status 7" — meaningless unless you know curl. Fix shipped in the
   canonical stage: the "Wait for application health" first step converts this
   into "Application health endpoint never returned 200". Recommendation:
   never remove that step; add the same guard before any step that calls the
   live service.
2. **Identity enforcement is gate-scoped, not pipeline-scoped.** The personal
   PMAK was refused by the quality gate, but the provision and behavioral
   steps (public API + Postman CLI) accepted it. If PayPal's policy is
   service-account-only everywhere, run the pinned
   `postman-resolve-service-token` check as the pipeline's first step.
3. **Harness platform quirks are invisible until they bite.** Versioned
   delegate tag, registry connector required on every K8s Run step,
   `account.harnessImage` path-rewriting, step memory limits, and the
   name regex (no commas or parentheses in pipeline/step names). All are
   pre-documented in `docs/PAYPAL-SERVICE-OWNER-INSTRUCTIONS.md`; the ease-of-use
   here is entirely documentation-borne, so keep that doc with the pipeline.
4. **Harness's own failure summaries are terse** ("exit status 1"). The
   canonical stages mitigate by echoing explicit `::error::`-style messages
   before exiting; any new step should follow that pattern so the Harness UI
   shows the reason without opening logs.

**Recommendations (in order of value)**
1. Publish the tools image to a postman-cs registry so PayPal pulls instead of
   builds — removes the last heavy setup step.
2. Promote the provision stage into the canonical stage set (it also bypasses
   the Spec Hub upload bug) once the public-API onboarding path is ratified.
3. Move the service-account identity check to pipeline step 1.
4. Keep health-wait guards in front of every live-service call.
5. Adopt the single-pipeline E2E shape (provision → route-contract → gate) as
   the default import; the three modules remain available individually for
   teams embedding into existing pipelines.
